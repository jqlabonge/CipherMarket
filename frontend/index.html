An on-chain marketplace for cryptographic vulnerability disclosure.

Flagship vertical: ECDSA nonce reuse. A seller claims a target account's signer reused a nonce across two signatures. The full finding stays hidden until a buyer pays into escrow -- payment only releases if the contract's own ecrecover-based check confirms both signatures really do recover to the target account over two different messages.

No oracle·No human judge·The math is the verifier

A listing alone is just a claim. Buying is what triggers the seller's reveal and the contract's own on-chain check -- that's the only thing that actually confirms a vulnerability is real, instead of someone on the internet saying your wallet is compromised.

Protocol flow
How a disclosure moves through the market

List → buy blind → reveal → verified on-chain, enforced entirely by the contract.

Walk through it →
  1. 1. List -- a hash, not the finding, goes on-chain

    Seller commits keccak256(findingText) plus public metadata (target account, category, severity, price) and posts a 10% stake. The finding text itself never touches the chain yet.

  2. 2. Buy blind -- only the affected account can pay

    Only the named targetAccount -- or a wallet it has explicitly authorized -- can pay the price into escrow. The eligibility check happens on-chain, not in this UI, so nobody else's purchase() call is even accepted.

  3. 3. Reveal -- automatic, math decides, not a referee

    The moment a purchase lands, the seller's browser automatically submits the full finding plus two ECDSA signatures sharing one r -- no manual step, no judgment call. The contract runs ecrecover on both. Match → escrow (price + stake) pays the seller and the finding is disclosed on-chain. Mismatch → buyer is refunded in full and receives the seller's slashed stake.

  4. 4. Timeout fallback -- nothing gets stuck forever

    If the seller never reveals within the window, anyone can call claimTimeout() and it resolves exactly like a failed reveal.

Show me →
  1. 1. Generate a demo vulnerability -- Simulate Vulnerable Target tab

    Open Simulate Vulnerable Target (marked Demo) and click "Generate synthetic vulnerable target." It creates a fresh keypair with a real, intentionally-reproduced nonce-reuse bug, standing in for a cryptographic finding you don't have on hand yet. Fund that address with a little Sepolia ETH if you plan to buy as it later.

  2. 2. List it -- Sell a Finding tab, or the Seller Agent

    Either fill out Sell a Finding yourself with the generated target address and evidence, or skip straight to Autonomous Agents (marked Demo) and let the Seller Agent generate and list a finding for you in one click -- paste a fixed target key there first if you want repeat runs to reuse the same demo account.

  3. 3. Buy it -- as the target account

    Only the target account (or its delegate) can buy. Switch MetaMask to that account (import the target's private key into it if it's a demo-generated one) and connect -- the "Buy for ... ETH" button then appears right on that listing's card.

  4. 4. See the proof -- reveal and verify

    If you used the Seller Agent, it auto-reveals once purchased. Listing manually? Use the Reveal tab as the seller. Either way, the listing card then shows what's compromised plus a "Deep dive into the proof" you can expand to see the raw signatures and derive the private key yourself.

Seller Agent (autonomous)

A deterministic finding-discovery-and-listing agent: it generates a synthetic "vulnerable target" keypair, runs the same toy signer used in "Simulate Vulnerable Target" to reproduce a genuine nonce-reuse instance, decides severity/price from simple rules, and submits the listing itself -- hash-committed, stake posted, no human writing a description or clicking "create." Pairs with the Buyer Agent below for a fully agent-to-agent trade with no human in the loop on either side. Demo data only -- see the Safety note in the README.

By default the agent generates a brand-new synthetic target every run, which is why you kept having to import a new MetaMask account. Paste a private key here once -- ideally the one for an account you've already imported and funded -- and every listing this agent creates will target that same address instead, so you only need one demo account for as many runs as you like. Saved in your browser only. Still synthetic/demo-only; never paste a real key here.

Buyer Agent (autonomous)

A simple deterministic purchasing agent: scans listings and auto-purchases anything matching its rule and where the connected wallet is actually eligible to buy (the on-chain contract enforces this either way). This demonstrates agent-to-agent commerce -- no human clicks "buy" for a matching listing.

Demo only. This generates a synthetic keypair with a real, intentionally-reproduced nonce-reuse bug so there's something genuine to list and prove, standing in for an actual disclosed vulnerability. Nothing here is a real finding or touches real funds.

Simulate a vulnerable target (demo data only)

Real signers derive each signature's nonce deterministically from the message (RFC 6979) specifically so nonces never repeat. To have something real to disclose in this demo, this generates a synthetic "target" keypair and a toy signer that intentionally reuses a nonce across two signatures -- entirely offline, in your browser, using toy-vulnerable-signer.js (no real key, no real funds, never sent anywhere). This is exactly the bug class the marketplace exists to disclose.
